infinity — identical to [ERFC](/docs/engineering/erfc), offered as a
naming-pattern sibling to [ERF.PRECISE](/docs/engineering/erf-precise).

## Return value

The complementary error function integrated between `x` and infinity.

## Description

ERFC.PRECISE computes exactly the same value as
[ERFC](/docs/engineering/erfc) — the two functions are interchangeable
for every input. Unlike the relationship between
[ERF](/docs/engineering/erf) and
[ERF.PRECISE](/docs/engineering/erf-precise) (where ERF has a genuine
extra capability, its optional `upper_limit` argument), ERFC never had
a two-argument form to begin with — both ERFC and ERFC.PRECISE always
integrate from `x` to infinity. ERFC.PRECISE exists purely to match
ERF.PRECISE's naming pattern.

## Common errors

### #VALUE! — x is nonnumeric

<ExcelCode>{`ERFC.PRECISE("x") → #VALUE!`}</ExcelCode>

`x` must be an actual number — text that can't be interpreted as one
returns `#VALUE!`.

### Assuming ERFC.PRECISE adds some capability ERFC lacks

<ExcelCode>{`ERFC.PRECISE(1) and ERFC(1) both return 0.1573 — truly interchangeable, unlike ERF vs ERF.PRECISE`}</ExcelCode>

Unlike [ERF](/docs/engineering/erf), which gains a genuinely useful
optional second argument over
[ERF.PRECISE](/docs/engineering/erf-precise), ERFC never had anything
analogous — ERFC and ERFC.PRECISE have always behaved identically,
with no functional difference to look for.

### Looking for an "ERFC with two arguments" form

<ExcelCode>{`ERFC(a, b) → #VALUE! (too many arguments) — ERFC only ever takes one argument`}</ExcelCode>

Neither `ERFC` nor `ERFC.PRECISE` has an `upper_limit`-style second
argument — they always integrate out to infinity, so there's no
"other end" to specify.
