## Return value

The error function integrated between `0` and `x`.

## Description

ERF.PRECISE computes exactly the same value as
[ERF](/docs/engineering/erf)'s one-argument form — `ERF.PRECISE(x)`
and `ERF(x)` always agree. The only real difference between the two
functions is that ERF.PRECISE has no optional second argument: it
always integrates from `0`, while ERF can additionally integrate
between two arbitrary bounds via its optional `upper_limit` argument.
ERF.PRECISE exists mainly as a naming-consistency sibling to
[ERFC.PRECISE](/docs/engineering/erfc-precise), both added to Excel
alongside each other.

<Callout type="warn">
  Microsoft's own VBA reference documentation for the
  `WorksheetFunction.Erf_Precise` method states that a negative `x`
  "generates an error" — but this appears to describe the older VBA
  automation wrapper specifically, not the `=ERF.PRECISE()` cell
  formula itself, which multiple independent sources confirm returns a
  correctly-signed negative result for a negative `x` (consistent with
  erf being an odd function). If a formula seems to behave differently
  than VBA code calling the same function, this kind of
  automation-layer-vs-worksheet-formula mismatch is worth keeping in
  mind.
</Callout>

## Common errors

### #VALUE! — x is nonnumeric

<ExcelCode>{`ERF.PRECISE("x") → #VALUE!`}</ExcelCode>

`x` must be an actual number — text that can't be interpreted as one
returns `#VALUE!`.

### Expecting a two-argument form, like ERF has

<ExcelCode>{`ERF.PRECISE(0.5, 1) → #VALUE! (too many arguments) — use ERF(0.5, 1) instead`}</ExcelCode>

ERF.PRECISE only ever takes one argument. To integrate between two
arbitrary bounds rather than from `0`, use
[ERF](/docs/engineering/erf)'s two-argument form instead.

### Assuming ERF.PRECISE is more accurate than ERF

<ExcelCode>{`ERF.PRECISE(1) and ERF(1) return the exact same value, 0.8427 — "PRECISE" isn't describing extra precision`}</ExcelCode>

Despite the name, ERF.PRECISE doesn't compute a more accurate result
than ERF — the two agree exactly for the same input. The "newer
function, clearer name" naming pattern (seen elsewhere in Excel, like
`CEILING.PRECISE`) doesn't always mean a precision improvement; here
it's purely a naming-consistency addition.
