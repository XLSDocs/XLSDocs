Compare two non-negative integers bit by bit, returning a number
whose bits are 1 only where **both** inputs had a 1 at that same
position — the function form of a bitwise AND.

## Return value

A decimal number representing the bitwise AND of `number1` and `number2`.

## Description

BITAND compares `number1` and `number2` one binary digit at a time.
For each position, the result has a `1` only if **both** numbers have
a `1` there — any position where either number has a `0` becomes `0`
in the result. This makes BITAND useful for testing whether a specific
bit (or set of bits) is turned on inside a packed value, since
AND-ing against a "mask" with only that bit set zeroes out everything
else.

<Callout type="warn">
  Both arguments are read as **decimal** numbers, not binary text —
  `BITAND(45, 21)` treats 45 and 21 as plain decimal integers and
  compares their binary representations internally. To AND two values
  that are already written as binary text (like `"101101"`), convert
  them with [BIN2DEC](/docs/engineering/bin2dec) first.
</Callout>

## Try it

<TryIt
  data={{ '21': '5', '60': '44', '0': '0' }}
  defaultValue="21"
  label={'Live preview — =BITAND(45, {value})'}
  fieldLabel="number2"
/>

45 is `101101` in binary and 21 is `010101` — the two only share a `1`
at positions 2 and 0 (worth 4 and 1), giving `000101` = **5**. Against
60 (`111100`), the shared `1`s land at positions 5, 3, and 2 (32 + 8 +
4), giving `101100` = **44**. AND-ing against 0 always returns 0,
since nothing can be "on" in both numbers when one of them has no bits
set at all.

## Common errors

### #NUM! — a negative number, a non-integer, or a value over 2^48-1

<ExcelCode>{`BITAND(-1, 5) → #NUM!`}</ExcelCode>

Both `number1` and `number2` must be non-negative integers no larger
than `281,474,976,710,655` (2^48-1). A negative number, a decimal like
`4.5`, or a value beyond that ceiling all return `#NUM!`.

### #VALUE! — a non-numeric argument

<ExcelCode>{`BITAND("abc", 5) → #VALUE!`}</ExcelCode>

Text that can't be read as a number returns `#VALUE!` rather than
`#NUM!` — that error is reserved for numbers that are out of range,
not for the wrong data type entirely.

### Mixing up AND with OR

<ExcelCode>{`BITAND(45, 0) → 0, not 45 — AND needs BOTH numbers to have the bit set`}</ExcelCode>

A common slip is expecting BITAND to behave like BITOR — "if either
number has this bit, keep it." BITAND is stricter: a bit only survives
into the result if it's set in **both** inputs, which is why AND-ing
anything against 0 always returns 0.
