Extract characters from the end of a string by byte count instead of
character count — the DBCS (double-byte character set) counterpart
of [RIGHT](/docs/text/right), kept for compatibility with older
workbooks built for Japanese, Chinese, or Korean editing
environments.

  **Microsoft's current documentation marks RIGHTB as deprecated.**
  It still works in every current Excel version for backward

  [RIGHT](/docs/text/right) is the function Microsoft now documents

## Return value

The rightmost portion of `text`, sized by `num_bytes` — counted in
bytes when a DBCS language is your default editing language, or in
characters (same as RIGHT) otherwise.

## Description

RIGHT and RIGHTB extract the same thing in almost every situation;
the only difference is the unit `num_bytes`/`num_chars` is measured
in. RIGHT always counts one unit per character. RIGHTB counts a
double-byte character (common in Japanese, Chinese, and Korean text)
as 2 units — but **only** when your Windows/Excel default editing
language is set to a language that supports DBCS. Otherwise, RIGHTB
counts one unit per character, identically to RIGHT.

<Callout type="info">
  **The switch depends on your Excel language settings, not on the
  text itself.** A cell containing Japanese characters doesn't make
  RIGHTB start counting bytes — it only does that if Japanese,
  Chinese (Simplified), Chinese (Traditional), or Korean is enabled
  and set as your default editing language. On an English-default
  install, RIGHTB returns the exact same result as RIGHT even against
  CJK text.
</Callout>

## Common errors

### #VALUE! — negative num_bytes

<ExcelCode>{`RIGHTB(A2, -1) → #VALUE!`}</ExcelCode>

Same restriction as RIGHT — `num_bytes` must be zero or a positive
number.

### Cutting a double-byte character in half

<ExcelCode>{`RIGHTB("日本語", 3) → an odd num_bytes can split a double-byte character under a DBCS default language`}</ExcelCode>

Under a DBCS default editing language, each CJK character is 2 bytes.
An odd `num_bytes` value can land in the middle of a character,
producing a garbled or unexpected result — use an even count, or
work in characters with RIGHT instead.

## Related functions

- [RIGHT](/docs/text/right) — the single-byte-set version of this
  function, and what Microsoft now recommends using instead.
- [LEFTB](/docs/text/leftb) and [MIDB](/docs/text/midb) — the other
  byte-counting extraction functions, for the start and the middle of
  a string respectively.
- [LENB](/docs/text/lenb) — often paired with LEFTB/RIGHTB to work
  out how many bytes remain in a string.

## Examples

<ExampleCard number="01" label="Basic — last 4 bytes" formula={`=RIGHTB(A2, 4)`}>
  On an English-default install, returns the same 4 characters RIGHT
  would. Under a DBCS default language, returns the last 4 bytes
  instead — 2 full-width characters.
</ExampleCard>

<ExampleCard number="02" label="Confirming identical behavior to RIGHT" formula={`=RIGHTB(A2, 4)=RIGHT(A2, 4)`}>
  Returns TRUE on any non-DBCS-default install, since RIGHTB only
  diverges from RIGHT when a DBCS language is your default editing
  language.
</ExampleCard>

<ExampleCard number="03" label="Default num_bytes (1 byte/character)" formula={`=RIGHTB(A2)`}>
  Omitting num_bytes returns just the last unit — a single character
  outside a DBCS default language, or potentially half of one
  double-byte character under a DBCS default language.
</ExampleCard>
