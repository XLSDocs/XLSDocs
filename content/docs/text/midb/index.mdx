Extract a chunk of text from any position by byte count instead of
character count — the DBCS (double-byte character set) counterpart
of [MID](/docs/text/mid), kept for compatibility with older workbooks
built for Japanese, Chinese, or Korean editing environments.

  recommends — use MIDB only if you're maintaining a workbook that

## Return value

A portion of `text`, starting at position `start_num` and sized by
`num_bytes` — counted in bytes when a DBCS language is your default
editing language, or in characters (same as MID) otherwise.

## Description

MID and MIDB extract the same thing in almost every situation; the
only difference is the unit `start_num`/`num_bytes` is measured in.
MID always counts one unit per character. MIDB counts a double-byte
character (common in Japanese, Chinese, and Korean text) as 2 units —
but **only** when your Windows/Excel default editing language is set
to a language that supports DBCS. Otherwise, MIDB counts one unit per
character, identically to MID.

<Callout type="info">
  **The switch depends on your Excel language settings, not on the
  text itself.** A cell containing Japanese characters doesn't make
  MIDB start counting bytes — it only does that if Japanese, Chinese
  (Simplified), Chinese (Traditional), or Korean is enabled and set
  as your default editing language. On an English-default install,
  MIDB returns the exact same result as MID even against CJK text.
</Callout>

## Common errors

### #VALUE! — invalid start_num

<ExcelCode>{`MIDB(A2, 0, 3) → #VALUE!`}</ExcelCode>

Same restriction as MID — `start_num` must be `1` or greater.

### Cutting a double-byte character in half

<ExcelCode>{`MIDB("日本語です", 2, 3) → an odd start position or byte count can split a double-byte character under a DBCS default language`}</ExcelCode>

Under a DBCS default editing language, each CJK character is 2 bytes.
A `start_num` or `num_bytes` that doesn't land on an even byte
boundary can split a character, producing a garbled or unexpected
result — use even values, or work in characters with MID instead.

## Related functions

- [MID](/docs/text/mid) — the single-byte-set version of this
  function, and what Microsoft now recommends using instead.
- [LEFTB](/docs/text/leftb) and [RIGHTB](/docs/text/rightb) — the
  fixed-end special cases of byte-based extraction MIDB generalizes.
- [FINDB](/docs/text/findb) and [SEARCHB](/docs/text/searchb) —
  locate a dynamic byte position to feed into MIDB's `start_num`.

## Examples

<ExampleCard number="01" label="Basic — extract a fixed segment" formula={`=MIDB(A2, 3, 4)`}>
  On an English-default install, returns the same 4 characters
  starting at position 3 that MID would. Under a DBCS default
  language, returns 4 bytes starting at byte 3 instead.
</ExampleCard>

<ExampleCard number="02" label="Confirming identical behavior to MID" formula={`=MIDB(A2, 3, 4)=MID(A2, 3, 4)`}>
  Returns TRUE on any non-DBCS-default install, since MIDB only
  diverges from MID when a DBCS language is your default editing
  language.
</ExampleCard>

<ExampleCard number="03" label="Dynamic start position with FINDB" formula={`=MIDB(A2, FINDB(" ", A2) + 1, 10)`}>
  Locates a starting position dynamically with FINDB, the same way
  MID is commonly combined with FIND.
</ExampleCard>
