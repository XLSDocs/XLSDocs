Find the position of text within another string, ignoring case and
supporting wildcards, counted by byte position instead of character
position — the DBCS (double-byte character set) counterpart of
[SEARCH](/docs/text/search), kept for compatibility with older
workbooks built for Japanese, Chinese, or Korean editing
environments.

  It still works in every current Excel version for backward

  [SEARCH](/docs/text/search) is the function Microsoft now documents

## Return value

The position of the first occurrence of `find_text` within
`within_text`, ignoring case — counted in bytes when a DBCS language
is your default editing language, or in characters otherwise. Returns
`#VALUE!` if `find_text` doesn't appear.

## Description

SEARCH and SEARCHB locate text the same way in almost every
situation; the only difference is the unit the returned position is
measured in. SEARCH always counts one unit per character. SEARCHB
counts a double-byte character (common in Japanese, Chinese, and
Korean text) as 2 units — but **only** when your Windows/Excel
default editing language is set to a language that supports DBCS.
Otherwise, SEARCHB counts one unit per character, identically to
SEARCH.

<Callout type="info">
  **The switch depends on your Excel language settings, not on the
  text itself.** A cell containing Japanese characters doesn't make
  SEARCHB start counting bytes — it only does that if Japanese,
  Chinese (Simplified), Chinese (Traditional), or Korean is enabled
  and set as your default editing language. On an English-default
  install, SEARCHB returns the exact same result as SEARCH even
  against CJK text.
</Callout>

Like SEARCH, SEARCHB is case-insensitive and supports `*`/`?`
wildcards — for a case-sensitive, literal-only search, use
[FINDB](/docs/text/findb) instead.

## Common errors

### #VALUE! — text not found

<ExcelCode>{`SEARCHB("x", A2) → #VALUE! (no "x" anywhere in A2, in any case)`}</ExcelCode>

Same behavior as SEARCH — wrap it in IFERROR if a missing match is a
valid, expected outcome.

### Expecting different results on an English-language install

<ExcelCode>{`SEARCHB("語", A2) → same result as SEARCH("語", A2), unless your default editing language is set to a DBCS language`}</ExcelCode>

If SEARCHB and SEARCH are returning identical results even against
CJK text, that's expected — the byte-counting behavior only activates
under a DBCS default editing language.

## Related functions

- [SEARCH](/docs/text/search) — the single-byte-set version of this
  function, and what Microsoft now recommends using instead.
- [FINDB](/docs/text/findb) — the case-sensitive, no-wildcards DBCS
  counterpart, paralleling SEARCH/FIND.
- [MIDB](/docs/text/midb) — often combined with SEARCHB's byte
  position to extract a DBCS substring.

## Examples

<ExampleCard number="01" label="Basic — case-insensitive byte position" formula={`=SEARCHB("語", A2)`}>
  On an English-default install, returns the same character position
  SEARCH would. Under a DBCS default language, returns the byte
  position instead.
</ExampleCard>

<ExampleCard number="02" label="Confirming identical behavior to SEARCH" formula={`=SEARCHB(" ", A2)=SEARCH(" ", A2)`}>
  Returns TRUE on any non-DBCS-default install, since SEARCHB only
  diverges from SEARCH when a DBCS language is your default editing
  language.
</ExampleCard>

<ExampleCard number="03" label="Wildcard match" formula={`=SEARCHB("語*", A2)`}>
  Wildcards work the same as in SEARCH — this matches any text
  starting with "語", regardless of what follows.
</ExampleCard>
