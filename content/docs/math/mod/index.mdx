## Return value

The remainder after dividing `number` by `divisor`. The result
always has the **same sign as `divisor`**, regardless of `number`'s
own sign.

## Description

MOD computes `number - divisor * INT(number / divisor)` — internally
built on the same floor-based rounding as [INT](/docs/math/int),
which is exactly why the result's sign follows `divisor`, not
`number`. This is the opposite convention from many programming
languages, where the remainder typically takes the sign of the
dividend instead. `MOD(7, 3)` is a familiar `1`, but `MOD(-7, 3)` is
`2` — not `-1`, which is what a language like Python's `%` on
integers would give for the equivalent unsigned case, or what naive
intuition expects.

<Callout type="warn">
  MOD's result always matches `divisor`'s sign, not `number`'s.
  `MOD(-7, 3)` returns `2` (positive, matching the positive divisor);
  `MOD(7, -3)` returns `-2` (negative, matching the negative
  divisor). This trips up anyone assuming the remainder should follow
  the number being divided.
</Callout>

## Common errors

### #DIV/0! — divisor is zero

<ExcelCode>{`MOD(10, 0) → #DIV/0!`}</ExcelCode>

There's no remainder to compute when dividing by zero — check that
`divisor` genuinely can't be zero before relying on MOD in a formula
that runs across a range.

### Expecting the remainder to match number's sign

<ExcelCode>{`MOD(-7, 3) → 2 (not -1, even though -7 is negative)`}</ExcelCode>

The result takes `divisor`'s sign, not `number`'s — this is standard
Excel behavior, not a bug. If a sign matching the dividend is
genuinely needed, the result has to be adjusted manually.

### Using MOD to test "every Nth row" and getting the offset wrong

<ExcelCode>{`MOD(ROW(), 2) = 0 → TRUE on even rows, not odd`}</ExcelCode>

`MOD(ROW(), 2)` is `0` on even rows and `1` on odd rows — a common
off-by-one mistake is assuming it flags odd rows instead, or
forgetting that row 1 itself returns `1`, not `0`.
