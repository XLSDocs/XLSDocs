Retrieve a single value from a table by matching a separate criteria
range against a database — but only when **exactly one** record
matches. DGET is built to fail loudly rather than guess, unlike most
lookup functions.

## Return value

The value in `field` for the single record matching `criteria`.
Returns `#VALUE!` if no record matches, and `#NUM!` if more than one
record matches.

## Description

DGET is a lookup function with a deliberately strict contract: it
only ever returns a value when the criteria uniquely identify one
record. This is the opposite behavior from VLOOKUP or XLOOKUP, which
silently return the *first* match and never warn about duplicates.

<Callout type="warn">
  DGET's all-or-nothing behavior is a feature for data validation: if
  criteria that should be unique (like an ID or an order number)
  ever match more than one row, DGET surfaces that as a `#NUM!` error
  instead of quietly returning the wrong record. Using DGET on a key
  that should be unique doubles as a duplicate-record check.
</Callout>

Like DSUM and DCOUNT, DGET's criteria range supports the same
AND-within-a-row, OR-across-rows structure — but since DGET requires
exactly one match, most real DGET criteria ranges use a single row of
AND conditions specific enough to isolate one record (an ID, or a
name plus a date).

## Common errors

### #VALUE! — no record matches

<ExcelCode>{`DGET(A1:D20, "Amount", F1:F2) → #VALUE!`}</ExcelCode>

No record in `database` satisfies every condition in `criteria`.
Double-check the criteria values for typos, and confirm the criteria
header text exactly matches a database header — a mismatched header
is silently ignored (same as in DSUM/DCOUNT), which can make criteria
that look specific actually match nothing.

### #NUM! — more than one record matches

<ExcelCode>{`DGET(A1:D20, "Amount", F1:F2) → #NUM!`}</ExcelCode>

More than one record satisfies the criteria. Either the criteria
aren't specific enough (add another condition, such as a unique ID),
or the underlying data has duplicate records that need cleaning up —
DGET just surfaced that duplication rather than hiding it.

### Wrong value returned entirely

This isn't actually possible with DGET the way it can happen with
VLOOKUP — DGET either returns the one unambiguous match or errors.
If a formula that looks like DGET is returning an unexpected value
silently, check whether it's actually a different lookup function
returning its "first match" instead.

## Related functions

- [DSUM](/docs/database/dsum) — sums a numeric field across every
  matching record, instead of requiring exactly one.
- [DCOUNT](/docs/database/dcount) — counts numeric values across
  matching records, instead of requiring exactly one.
- [XLOOKUP](/docs/lookup/xlookup) — returns the first matching value
  without erroring on duplicates, the opposite tradeoff from DGET.
- [VLOOKUP](/docs/lookup/vlookup) — the classic single-match lookup;
  like XLOOKUP, it never checks for duplicate matches the way DGET does.
