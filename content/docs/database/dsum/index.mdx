Sum a numeric column across all the rows in a table that satisfy
conditions listed in a **separate criteria range**, instead of
conditions written directly into the formula — the same underlying
mechanic as Excel's classic Advanced Filter.

## Return value

The sum of `field` across every record in `database` that matches
every condition in `criteria`. Returns `0` if no records match.

## Description

DSUM's criteria range is a small table of its own: a header row
copied from (or matching) the database's headers, with condition
values underneath. The rules that make it powerful, and occasionally
confusing:

- **Two conditions on the same row** are combined with **AND** — a
  record must satisfy both to count.
- **Two conditions on separate rows** are combined with **OR** — a
  record matching either row counts.
- A criteria column can be left blank to mean "no condition on this
  field."

<Callout type="warn">
  The criteria range's headers must **match the database's headers
  exactly** — same text, same case is fine, but not a typo or a
  synonym. A header that doesn't exist in the database makes DSUM
  ignore that row of criteria entirely rather than throwing an error,
  which is a quiet way for a formula to silently stop filtering.
</Callout>

This OR-across-rows behavior is the one thing DSUM can do that
SUMIFS can't do directly: SUMIFS combines every condition with AND,
so expressing "Region is East OR Region is West, AND Amount > 1000"
needs either two SUMIFS calls added together or an array formula.
DSUM expresses it as two criteria rows.

## Common errors

### The result is 0, but matching rows clearly exist

The most common cause is a criteria header that doesn't exactly match
a database header — a trailing space, a different word, or a merged
cell copied incorrectly. Since DSUM doesn't error on a bad header, it
just silently returns 0 instead of pointing at the mistake.

### #VALUE! from the field argument

<ExcelCode>{`DSUM(A1:D10, "Amont", F1:G2) → #VALUE!`}</ExcelCode>

`field` was passed as text but doesn't match any header in `database`
at all (not even a near-miss inside the criteria range — this is the
database's own headers). Check the spelling against the database's
actual header row.

### Numbers stored as text aren't summed

Like SUM and SUMIFS, DSUM only totals genuine numeric values. A
column of numbers formatted or entered as text (common after a CSV
import) will be skipped, understating the total without any error.
