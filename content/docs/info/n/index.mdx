Convert a value to a number — but not by *parsing* text the way
[VALUE](/docs/text/value) does. N follows a fixed, narrow set of
conversion rules: numbers pass through unchanged, `TRUE`/`FALSE`
become `1`/`0`, dates become their serial number, and **text becomes
`0`**, not a parsed number.

## Return value

A number, following these rules: a number returns unchanged; `TRUE`
returns `1`; `FALSE` returns `0`; a date returns its serial number;
**any text returns `0`**, regardless of whether it looks numeric; an
error value passes through as that same error.

## Description

N is easy to confuse with [VALUE](/docs/text/value), but they do
very different things with text. VALUE actually parses a numeric-
looking string (`"7"` becomes the number `7`). N does not parse text
at all — any text input, numeric-looking or not, simply becomes `0`.
Microsoft documents N as existing mainly for compatibility with
other spreadsheet programs that require an explicit conversion
function; Excel itself usually converts values automatically where
needed, without N being necessary.

<Callout type="warn">
  **N does not parse numeric text — it discards it.** `N("7")`
  returns `0`, not `7`. Reaching for N expecting VALUE's behavior is
  a common mix-up between the two; use VALUE directly whenever text
  needs to become the number it represents.
</Callout>

## Common errors

### Expecting N to parse numeric text like VALUE does

<ExcelCode>{`N("42") → 0, not 42 — use VALUE("42") instead for actual parsing`}</ExcelCode>

N only converts a fixed set of non-text types; text always becomes
`0` regardless of its content.

### Using N where it adds nothing

<ExcelCode>{`N(A2) → the same number A2 already holds, if A2 is already numeric`}</ExcelCode>

For an already-numeric cell, N is a no-op — Excel uses the number
directly in arithmetic without needing N to convert it first.
