The report worked fine in testing. Then someone ran it against a full
year of data instead of a sample month, and Excel froze for four
minutes. Nothing was wrong with the formula's logic — it was wrong
about how much work it was actually asking Excel to do.

## The formula in question

<ExcelCode>{`=SUMPRODUCT(--(A$2:A$50000=A2))`}</ExcelCode>

A per-row "how many other rows match this one" count, copied down
50,000 rows. Each cell scans the entire 50,000-row range. Copy it down
50,000 times, and that's 50,000 × 50,000 comparisons — 2.5 billion —
for a calculation that conceptually only needs one pass over the data.

## Why this is easy to miss

The formula is correct. It returns the right answer on a 500-row test
sheet in well under a second, because 500 × 500 is nothing. The
problem only shows up at production scale, which is exactly when it's
most expensive to discover.

<Callout type="warn">
  Any formula that scans a full range **and** is copied down that same
  range is quadratic — the total work grows with the *square* of the
  row count, not linearly with it. Doubling the data doesn't double
  the calculation time, it quadruples it.
</Callout>

## The linear-time fix

COUNTIF-family functions and PivotTables use internal indexing that a
manual `SUMPRODUCT`/array-formula scan doesn't get:

<ExcelCode>{`=COUNTIF(A$2:A$50000, A2)`}</ExcelCode>

Same result, but COUNTIF is implemented to avoid the naive
row-by-row rescan — on the same 50,000 rows, this runs in a fraction
of a second instead of minutes.

## The general pattern to watch for

Whenever a formula's `range` argument is the *same* range the formula
is copied down, ask what happens as that range grows. If the honest
answer is "it gets scanned once per row," you have a quadratic
formula, whether or not the syntax looks dangerous. The fix is almost
always the same shape: reach for a function built with an index behind
it (COUNTIFS, SUMIFS, XLOOKUP with binary search mode, a PivotTable)
instead of a manual array comparison, or restructure so the expensive
range only gets scanned once — for example, computing the count in a
PivotTable or a single helper table instead of once per row.
